MaaNTE is built on two main layers that work together: declarative pipeline JSON files that describe task graphs, and Python custom actions that handle logic too complex for a pipeline alone. MaaFramework drives both — it reads the pipeline definitions, performs image recognition against the game window, and calls into Python when a task node requires it. MFAAvalonia provides the GUI on top without requiring any additional code.

## Architecture

### Pipeline JSON tasks

Pipelines live in `assets/resource/base/pipeline/` as JSON files. Each file defines a set of task nodes. A node describes a recognition condition (for example, matching a template image within a region of the screen) and an action to perform when that condition is met — clicking, swiping, waiting, or calling a custom Python action. MaaFramework traverses these task graphs at runtime, advancing through nodes as conditions are satisfied.

This approach keeps most automation declarative. Adding a new step to an existing workflow often means adding or editing a JSON node rather than writing code.

### Python custom actions

When a task requires logic that pipelines cannot express — iterative algorithms, OpenCV-based matching, stateful control loops — a Python custom action handles it. Custom actions live in `agent/custom/action/` and are registered with MaaFramework's agent server using the `@AgentServer.custom_action` decorator. The pipeline references the registered name as a string; MaaFramework invokes the Python class at runtime.

The agent process (`agent/main.py`) manages the virtual environment, installs dependencies from `requirements.txt`, and starts the agent server that MFAAvalonia connects to.

### MFAAvalonia GUI

MFAAvalonia reads `assets/interface.json` to generate the task selection UI and option controls. No GUI code is required — adding a new task to `interface.json` automatically surfaces it in the interface.

## How contributions work

MaaNTE follows a standard fork-and-PR workflow:

1. Fork the repository on GitHub.
2. Clone with submodules and set up your local environment.
3. Make changes on a feature branch.
4. Open a pull request targeting the `dev` branch — not `main`.

The `dev` branch is the integration target for new work. The `main` branch tracks stable releases.
